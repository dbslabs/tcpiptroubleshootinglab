Lab Overview

In this exercise you and your partner act as network technicians responding to fault reports on the isolated 172.16.100.x/24 subnet. One of you runs the diagnostic commands while the other acts as the remote host. You swap roles between scenarios.

This lab is not graded. The goal is to practice using each command until it feels natural and you understand what its output is telling you. Each scenario presents a symptom, guides you to the right command, and asks you to apply a fix.

Command Reference

Review this table before starting the scenarios:

Command What It Shows When to Use It
ipconfig IP address, subnet mask, and default gateway for each adapter Quick sanity-check that an address is assigned and correct
ipconfig /all Full detail: MAC address, DHCP enabled/disabled, DNS server address, lease times Deep-dive when basic config looks wrong or DHCP is suspect
ipconfig /release Releases the current DHCP lease without requesting a new one Pair with /renew to force a fresh DORA cycle
ipconfig /renew Drops current DHCP lease and requests a new one from the DHCP server When DHCP address is missing, stale, or shows 169.254.x.x
ipconfig /displaydns Shows the local DNS resolver cache (recently looked-up names and their IPs) Check whether a cached entry is stale or incorrect
ipconfig /flushdns Clears the DNS resolver cache entirely Force a fresh DNS lookup after editing the hosts file
nslookup <hostname> Queries the configured DNS server and returns what it knows about the hostname Test whether 8.8.8.8 can resolve a public name
nslookup <hostname> <server> Queries a specific DNS server instead of the default Compare results between 8.8.8.8 and a local source
netstat -an All active TCP/UDP connections and listening ports with their states Check if a service is running and whether a session is established
netstat -n Active connections with numeric IPs only (no DNS reverse lookup) Faster output when you only need IP addresses and ports
arp -a ARP cache: all known IP-to-MAC address mappings on the local subnet Verify Layer 2 reachability; detect IP address conflicts
arp -d * Clears the entire ARP cache Force fresh ARP resolution after an address change or conflict fix
ping <IP> Tests basic ICMP reachability to a host Always the first test in any troubleshooting sequence

Troubleshooting Method: Work Bottom-Up

Always start at the lowest layer and work upward. Fixing a higher-layer problem while a lower-layer problem exists is wasted effort.

  1. Physical: Is the cable plugged in? Is the adapter enabled in Device Manager?
  2. IP Configuration: Does the machine have the correct IP, mask, and gateway?
    Commands: ipconfig and ipconfig /all
  3. Reachability: Can packets travel between the two machines?
    Command: ping 172.16.100.11
  4. ARP: Does the machine know the MAC address of the target?
    Command: arp -a
  5. Name Resolution: Can the hostname be translated to an IP address?
    Commands: ipconfig /displaydns, ipconfig /flushdns, and nslookup (for public names).
    Important: 8.8.8.8 will NOT resolve local lab hostnames. Use the hosts file for local names.
  6. Transport Service: Is the destination service actually listening on the expected port?
    Command: netstat -an

Warm-Up: Capture a Healthy Baseline

Before any fault scenario, run the sequence below to record what a working network looks like. If you spot a problem during the warm-up, tell your instructor before proceeding.

  • Step 1 — Quick IP check: Run ipconfig.
    Expected: IP 172.16.100.10, Mask 255.255.255.0, Gateway 172.16.100.1. If any value is wrong, stop and fix it before continuing.
  • Step 2 — Full detail check: Run ipconfig /all.
    Listen for: Physical Address (your MAC address), DHCP Enabled (Yes or No), and DNS Servers. The DNS server should show 8.8.8.8. Note all three values for comparison later.
  • Step 3 — Reachability test: Run ping 172.16.100.11.
    Expected: four replies with 0 percent packet loss. If ping fails, troubleshoot IP configuration before any other step.
  • Step 4 — ARP cache check: Run arp -a.
    After a successful ping, your partner's IP 172.16.100.11 should appear with their MAC address. If the same IP shows two different MACs, there is an IP conflict. Report it to your instructor immediately.
  • Step 5 — DNS cache and hosts file check: Run ipconfig /displaydns.
    The cache will likely be empty at the start of the lab. That is normal with 8.8.8.8 as the DNS server, because no public lookups have been made yet. Local lab hostnames are not in the cache because 8.8.8.8 does not know them.
    To verify local name resolution, check the hosts file located at C:\Windows\System32\drivers\etc\hosts. Open it with Notepad run as Administrator. Each line maps a hostname to an IP address. A correct entry for your lab looks like:
    172.16.100.11 pc2-student-b
    If this line is absent or incorrect, local hostname resolution will fail even though 8.8.8.8 is working perfectly.
  • Step 6 — nslookup test (public name only): Run nslookup google.com.
    This tests whether 8.8.8.8 is reachable and responding. A successful result returns an IP address for google.com. If this fails, there is a connectivity or DNS server problem outside your subnet.
    NOTE: Do NOT use nslookup to look up local lab hostnames such as pc2-student-b. Because 8.8.8.8 is your DNS server, it will always return a failure for local names. Use the hosts file instead.
  • Step 7 — Active connections check: Run netstat -an.
    At baseline there should be no ESTABLISHED sessions unless other software is running. Note any ports already in LISTENING state.

Troubleshooting Scenarios

Work through each scenario in order. Read the fault report, choose the right command, run it, interpret the output, and apply the fix. Discuss every step with your partner before moving on.

Scenario 1: The Mystery Address

Fault report: Your machine cannot reach 172.16.100.11 even though the cable is plugged in. A classmate changed some settings and you do not know what they changed.

Your Task: Use ipconfig to diagnose the problem from the command line only. Do not open any GUI network settings panels.

  1. Run ipconfig and listen carefully to every value.
    IPv4 Address . . . . : 192.168.1.50
Subnet Mask  . . . . : 255.255.255.0
Default Gateway  . . : 192.168.1.1
    The address 192.168.1.50 is on a completely different network. Your machine cannot reach anything on 172.16.100.x until this is corrected.
  2. Run ipconfig /all to determine whether this is a static address or a DHCP mistake.
    Listen for DHCP Enabled. If it says No, someone manually entered the wrong address. If it says Yes, the DHCP server handed out an address from the wrong pool.
  3. Fix the address:
    - If static: open network adapter properties and set IP to 172.16.100.10, mask to 255.255.255.0, gateway to 172.16.100.1.
    - If DHCP: force a fresh lease:
    ipconfig /release
    ipconfig /renew
  4. Verify the fix with ipconfig (confirm 172.16.100.10) and test reachability via ping 172.16.100.11.

Discussion Questions — Scenario 1:

  • How did ipconfig alone reveal the problem before you even tried to ping?
  • What is the difference between a wrong IP address and a missing IP address?
  • Why can a machine on 192.168.1.x never reach 172.16.100.x without a router?

Scenario 2: The Hostname That Goes Nowhere

Fault report: You can ping 172.16.100.11 by IP address but when you try to connect using the hostname pc2-student-b, nothing works. Your partner has a service running on port 8080.

Background: Your DNS server is 8.8.8.8, which knows public websites like google.com but has no knowledge of private local names like pc2-student-b. Local name resolution uses the hosts file.

Your Task: Investigate the hosts file and the DNS cache, then verify the service is running.

  1. Check the DNS cache first: ipconfig /displaydns.
  2. Open the hosts file in Notepad as Administrator: C:\Windows\System32\drivers\etc\hosts.
    A correct entry sounds like: 172.16.100.11 pc2-student-b. Add or correct the line if missing.
  3. Flush the DNS cache: ipconfig /flushdns.
  4. Verify the hosts entry in cache: ipconfig /displaydns.
  5. Confirm with nslookup pc2-student-b.
  6. Check port 8080 on your partner's machine using netstat -an. If absent, start the listener: nc -l -p 8080.
  7. Connect from your machine: nc pc2-student-b 8080.

Discussion Questions — Scenario 2:

  • Why will nslookup always fail for local lab names when the DNS server is 8.8.8.8?
  • What is the hosts file and at what point in the name resolution process does Windows consult it?
  • Why do you need to run ipconfig /flushdns after editing the hosts file?
  • What does it mean when nslookup returns the correct IP but the connection to port 8080 still fails?

Scenario 3: The Ghost on the Network

Fault report: Connectivity to 172.16.100.11 is intermittent. Sometimes ping works, sometimes it times out. Your instructor suspects an IP address conflict.

Your Task: Identify and verify the IP conflict using ARP.

  1. Ping your partner: ping 172.16.100.11.
  2. Check the ARP cache: arp -a. (Healthy sounds like: 172.16.100.11 aa-bb-cc-dd-ee-ff dynamic).
  3. Clear the cache and repeat: arp -d *, then ping 172.16.100.11, then arp -a.
  4. Identify any unrecognized MAC address against known lab machine MACs.
  5. Fix the conflict by reassigning the conflicting device's IP, clear cache, and retest.

Discussion Questions — Scenario 3:

  • Why does intermittent connectivity point toward an IP conflict rather than a faulty cable?
  • At what layer of the TCP/IP model does ARP operate, and why is it specific to the local subnet?
  • What would happen on a large production network if two servers shared the same IP address?

Scenario 4: Renew Fails After a Power Cut

Fault report: After a power cut, your machine came back with an address starting with 169.254 (APIPA address), meaning DHCP failed.

Your Task: Investigate and recover DHCP connectivity.

  1. Confirm APIPA address with ipconfig.
  2. Check full details with ipconfig /all.
  3. Attempt gateway ping: ping 172.16.100.1 (Expected: Request timed out).
  4. Force a new lease:
    ipconfig /release
    ipconfig /renew
  5. Verify restoration with ipconfig and ping 172.16.100.11.

Discussion Questions — Scenario 4:

  • What is the DORA process and which specific step fails when you end up with an APIPA address?
  • Why can two APIPA machines sometimes communicate with each other but not with the rest of the network?
  • What is the difference between ipconfig /release and ipconfig /renew? Do you always need to release before renewing?

Scenario 5: The Port That Was Not Listening

Fault report: You are trying to connect to a service on 172.16.100.11 port 5000 and receive "Connection refused" every time, even though both machines can ping each other.

Your Task: Verify transport layer listeners and resolve the connection.

  1. Attempt connection: nc 172.16.100.11 5000 (Listen for Connection refused).
  2. Have your partner check ports with netstat -an for LISTENING state.
  3. Partner starts listener: nc -l -p 5000 and verifies with netstat -an.
  4. Retry connection, type a message, and verify ESTABLISHED state on both machines using netstat -an.

Discussion Questions — Scenario 5:

  • What is the difference between Connection refused and Request timed out? What does each error tell you about where the fault is?
  • Why does netstat show ESTABLISHED on both machines simultaneously during an active TCP session?
  • If netstat showed port 5000 in LISTENING state but the connection still failed, what would you check next?
